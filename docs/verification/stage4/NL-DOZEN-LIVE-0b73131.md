## 已核验的调用链根因

### 模型自行增加了错误业务条件

D02 冻结预期为 `amount_cents >= 100000`，独立 SQL 得到 6 张、1,064,067 分。模型却把错字“金颚”解释为销售方，增加 `seller_name LIKE '%金颚%'`；后续又按销售方分组，始终没有恢复原目标。它没有就疑似错字追问。这是本批明确的业务理解错误，不能归为单纯界面问题。

### 执行器支持的 SQL 大于范围证据支持的 SQL

D03 原始 SQL 正确按银行方向分组，收入为 4 笔、13,000.50 元；D05 原始 SQL 正确查询 C002 九月的 F002、F008，两票备注均为空，转述没有被执行。

`business_sql._query_scope` 只处理有限的直接查询：分组返回未知范围，日期条件只识别月前缀 LIKE；这些场景使用合法分组或 `>=`、`<`、`<=` 日期范围，得到 `query_scope.scope=None`。`responses.reply_evidence_conflict` 随即返回 `unverified_query_scope`，工作台拒绝显示模型原文。查询本身与独立 SQLite 结果一致。

### 信封类型和待补生命周期仍会脱节

D08 第一轮模型文字明确询问 F011 还是 F018，却返回 `kind=information`，没有 `missing_fields` 或 `pending_change`。运行时只有在结构化追问路径才保存待补项，所以记录为空；取消轮仍未得到实际取消状态。两轮都没有误生成预览或写入。

### 日期字面量没有区分锚点和目标

D10 模型第二轮调用参数为 C002 / 2026 / 8；Trace 中 Harness 的 `requested_scope` 却仍为 C002 / 2026 / 9。字面量提取把“刚才九月”锁成目标，忽略它是“前一个月”的参考锚点。范围保护确实阻止了执行，但阻止的是正确参数。

### 合法单位换算触发数字白名单

D13 返回的规则文本保存 `100000分`，模型解释为 `1000元` 正确。当前字面量检查只对部分 `_cents` 数值字段转换，对规则正文中的数值没有按单位归一，所以将 1000 判为 `unbound_reply_literals`。版本 1.0 停用、版本 2.0 启用及生效日期本身均正确。

后续修复应处理这些机制及证据表示，保留权限、范围和确认约束；本轮不实施修复。
