# 财税自然语言处理统一改造方案

本方案细化 [模型回复与范围绑定根因](MODEL-REPLY-ROOT-CAUSES.md) 中 NL-01 至 NL-06 的统一修复。运行代码基线为 `26344f0`，方案阶段尚未实现。目标是在已有单模型循环中，让陌生表达进入同一条业务链，并复用权限、查询、确认、事务和审计能力。

方案的核心是有限的业务结构与开放的语言表达：模型将原话转换为可组合的业务操作，程序检查对象、数据和执行边界。业务意图矩阵只用于覆盖评估与验收，不成为运行时问句库、向量匹配库或关键词路由表。

本轮限定在现有业务能力的自然语言入口和会话接续。长上下文扩展、多会话能力和 GUI 继续按原路线排后，不混入本次重构。

## 一 约束和取舍

1. 一轮只有一个模型循环、一份当前业务意图、一套业务事实来源。模型理解、工具选择、追问和语言回复使用同一模型，不增加分类模型、规划模型或回答评委。
2. 不以原话匹配决定能否提案、能否保存待补状态或是否展示模型正文。命令、按钮和格式检查可以确定处理；自然语言动作交给模型。
3. 不要求模型每轮输出长计划、理由、置信度或完整业务矩阵。只声明本轮实际需要的操作及接续变化，缺少什么就保留什么。
4. 读取范围与各项修改范围分别绑定。禁止再以整句话中出现的所有票号组成修改全集。
5. 模型语义候选、当前数据事实和执行许可分别处理。可引用的原文能够证明来源存在，不能自动证明模型正确理解了原文。
6. 迁移以业务能力为单位；已迁移能力使用唯一入口。新入口失败时返回明确状态，不能悄悄回退到关键词旧入口。

## 二 最小的业务语义结构

业务操作由稳定的维度组合：执行效果、资源、范围、对象选择、字段变化、来源引用和缺项。无需为“换个说法查两票”“带否定的改备注”“补号后查改”分别新增意图类别。

| 结构 | 含义与边界 |
|---|---|
| `operations` | 本轮有界的操作列表；每项有本轮唯一 `op_id`。效果使用读取、说明、修改提案等少数类型，资源和实际工具能力取自注册表。 |
| `scope` | 企业、目标账期和规则参考日期分别记录。跨企业或多账期属于不同操作范围，不能压平为一组全局槽位。 |
| `selector` | 明确联合键、可信展示锚点，或实际查询结果的引用。不同操作可以读取同一集合，并只修改其中一个明确子集。 |
| `changes` | 允许字段、拟修改值及其原文引用。备注文本中的业务词语只属于值，不能再作为路由输入。 |
| `preserve` | 明确保留的对象或字段，绑定相应操作；独立于查询集合，也不等同于一个全局排除票号列表。 |
| `sources` | 原始消息、已有待补项、展示锚点及实际工具结果的引用。引用内容由运行时读取，不能接受模型提交的伪造来源正文。 |
| `missing` | 缺项绑定具体操作及所阻断的阶段。某项修改缺票号不妨碍其他明确的查询完成。 |
| `continuation` | 新请求、补充、更正或取消，以及被作用的待补记录和版本。没有唯一旧对象时保留待补，不依靠“最近一个”猜测。 |

筛选和聚合继续使用已有只读 SQL、查询工具及规则工具。本轮不再开发一套与 SQL 平行的完整筛选语言，也不把自由文本条件复制到多个状态对象中分别解析。

Schema 使用封闭字段与类型，操作列表受已有预算和批量上限约束；它不是可运行脚本或通用工作流 DAG。先只表达现有工具能完成的操作，遇到尚不支持的组合明确给出未完成项，不生成新工具或静默丢弃子目标。

下例只是语义示意，省略必需的来源引用与协议版本：

```json
{
  "operations": [
    {"op_id": "read", "effect": "read", "resource": "invoice", "scope": {"company_id": "C002", "year": 2026, "month": 8}, "selector": {"invoice_nos": ["F012", "F015"]}, "fields": ["purpose"]},
    {"op_id": "edit", "effect": "propose_change", "resource": "invoice", "scope": {"company_id": "C002", "year": 2026, "month": 8}, "selector": {"invoice_nos": ["F015"]}, "changes": [{"field": "remark", "value": "展会住宿凭证待归档"}]}
  ],
  "preserve": [{"op_id": "edit", "fields": ["purpose"]}],
  "missing": []
}
```

同一意思的语序变化、错别字和中英混写应产生等价操作。只有业务含义改变，才改变操作数据。新增问法只增加测试样本；新增字段或业务能力才可能改变结构和工具。

## 三 工具协议和同批调用

增加一个运行时原生工具 `declare_business_intent`。它接收最小语义候选、做结构和引用核验，不访问业务表执行写入，也不产生确认许可。

模型可以在一次响应中依次发出意图声明和已有查询工具调用。声明中的 `op_id` 由模型在当前响应内命名，后续同批调用即可引用；不要求模型预知声明执行后才产生的服务端编号。运行时将其绑定到实际会话、本轮 Trace 和记录版本。同名 `op_id` 不能跨轮带来任何权限。

在工具 Schema 构建与参数校验处统一增加 `intent_operation_id`，校验后剥离再调用现有业务 Handler，不逐个复制业务工具实现。只有一个匹配操作时可以省略引用；存在两个可匹配操作则必须指定。实际提案仍必须引用本轮真实查询生成的 `selection_id`，意图引用不能替代选集。

同批处理严格按模型给出的顺序逐项执行。依赖未就绪、引用错误或声明失败时，依赖工具返回相应失败并保留 `tool_call_id` 配对；不重排、不猜测引用、不偷偷执行。实际工具请求和模型修正都计入现有预算。

无需查询的直接回答或追问可以在最终信封提交相同结构，经过同一个校验器。已声明的记录在最终信封中只引用，不重复提交另一份可变意图。发生变化必须提交明确版本更新，不能用最后一段正文隐式改范围。

这一设计不会强制增加一次模型往返，但会增加少量结构化输出。是否能稳定同批调用及其实际 token、耗时，要在实现后的 DeepSeek Trace 中测量，不能从方案推定。

## 四 核验做到什么程度

| 检查 | 程序可以确定的事实 |
|---|---|
| 身份与账簿 | 可信 Session、实际账簿身份、当前企业权限及记录归属。 |
| 来源引用 | 原始消息存在且属于当前可用会话；片段匹配原文；锚点可见；工具结果真实存在。 |
| 实体归一 | 企业标识按现有可信别名表映射；票号、年月、金额按明确格式归一。疑似 F01O/F010 等存在实质歧义时追问，不凭相似度替换。 |
| 对象和范围 | 操作独立范围、选集归属、本轮查询证据、实际账期和保留约束一致。企业或年月来源不能用“账号有权访问”代替。 |
| 字段与值 | 只改允许字段；备注和用途新值核对用户原文。显式清空作为独立取值动作处理，不能把空串同时当“没提供”。 |
| 执行阶段 | 模型只能提出候选；准备、确认、提交、审计和回读依据实际系统状态。 |

来源片段优先引用消息编号及原文片段，由运行时定位；重复片段需补充位置。若使用字符区间，按 Python 字符索引验证完整片段，避免把模型报的偏移直接当作有效证据。企业别名是数据字典；“查、看看、核一下”等动作同义词不建立运行时字典。

相对日期使用运行时提供的日期、时区和明确业务日期锚点归一；目标账期与规则参考日期分开。没有可靠锚点就追问，不把样本账期、历史月份或当前月份悄悄当默认值。

程序不能仅凭类型和片段存在证明“这句话真的要求修改”“引号内是转述还是本次命令”。这部分仍由模型理解，并用独立语言验收检验。模型两次输出相同结论或自报高置信度也不能补成事实。错误预览同样算失败，即使最终没有提交。

金额与数量由业务服务、SQLite 和规则计算。模型负责表达，回复可引用真实结果编号。存在可机检的引用或数值冲突时，让同一个模型有限修正；不能声称通过结构检查便已证明任意正文无误，也不能为修正正文重新堆中文关键词。

现有 `ScopeProof` 继续表达执行范围证据；意图记录表达模型的候选业务含义。由核验器把可核验的引用映射为逐操作范围证明，不将模型提交的 `sources=user_current` 直接复制成可信来源。旧查询、旧草稿、历史金额和意图记录均不产生当前提交许可。

## 五 跨轮状态只保留一个可变所有者

Agent 持有唯一的会话级待补记录。记录包含绑定身份与账簿、版本、原请求引用、操作、缺项、候选锚点、各字段来源和执行阶段。已有长期任务、偏好、展示引用、草稿和事务仍由各自模块持有；这里只保存引用，不复制其权威状态。

`InvoiceQueryChain` 当前固定为 first/second 两个位置。迁移后将查询待补项表达为同一记录中的操作列表，先保留现有业务数量上限；链对象只在过渡期做只读展示投影，不能与 `pending_intent` 各自修改一份业务意图。

模型读到结构化待补状态和必要原文后，提交对指定记录版本的补充、更正、取消或新请求。程序核验后一次性应用变化；非法版本或引用冲突不部分覆盖原记录。接口不靠字符串拼接成一句“标准中文”再交给下游重解析。

| 场景 | 状态处理 |
|---|---|
| 查两张、稍后选一张改备注 | 查询操作可完成；修改操作等待目标，保留字段、新值和候选锚点。 |
| “另一张不动，就 F018” | 模型补充修改目标，程序核对原候选、旧值来源和当前数据；只准备 F018。 |
| 更正企业、月份、目标或新值 | 更新明确槽位并使受影响选集及草稿失效；不同企业不能借用旧企业候选。 |
| 插入一个新查询 | 可独立执行，原待补记录仍可见；是否替换或取消必须有明确结构化动作，多项可能时追问。 |
| 自然语言终止 | 模型指明取消对象；程序清除相应待补或未提交草稿，不撤销历史已提交业务。 |
| 可信取消按钮、命令、身份或账簿切换 | 程序直接使相关执行许可失效；自然语言还未理解也不影响明确的界面终止。 |
| 网络失败或预算用尽 | 记录真实已完成项和仍待补项；不生成模板业务成功，也不自动提交。 |

是否有多个待补候选与是否允许多个持久任务分别遵守现有约束。本轮不增加持久任务并发能力或跨会话自动恢复提交。

## 六 模块边界和必须撤掉的旧路径

建议新增两个小模块：`intent_contract.py` 放数据结构、协议与纯校验；`intent_binding.py` 将引用绑定到实际消息、Session、范围及查询证据。状态更新仍由 Agent 的一个明确入口负责，不创建包办上下文、权限、调度和业务的控制器。

| 现有位置 | 改造职责及退出条件 |
|---|---|
| `agent.py` 的模型前处理 | 移走自然语言句式拆分、补充句拼接、自然语句取消和关键词工具开关。保留可信命令、身份状态与尚未解决的执行结果所要求的限制。 |
| `tui_intent.py` | `named_invoice_read_and_edit`、`invoice_choice_reply`、`invoice_followup_action`、`invoice_supplement` 不再裁决迁移后的自然语言路径。删除无调用的分支；格式归一与可信命令解析独立保留。 |
| `ContextBuilder.begin/proof`、`responses.explicit_scope` | 已迁移入口接收核验后的逐操作范围，不再先用整句提取结果锁死模型。上下文仅组装必要信息，已有引用解析器仍核验实际锚点。 |
| `invoice_batch.plan_invoice_change` | 接收核验后的修改操作和真实 selection，保留权限、账期、规则、当前值、数量限制和事务边界。业务层不读取语义模型，也不解析中文。 |
| `_rule_subset_filters` 与规则集合判断 | 用当前规则结果与已有查询选集做可复核的集合核对，不再从“或”“销售方”等字样猜筛选。规则全集完整性、交集及排除项按实际键核验；SQL 表达与用户原话的语义一致性仍须验收。 |
| Registry 与 Handler | 共用协议附加字段和能力声明；真实业务校验沿用服务。修改候选工具可见性由可信模式与阶段决定，不依据原话是否出现动作词。 |
| `responses.py`、`Agent.finish`、TUI/CLI | 模型正文、结果卡、系统回执分别承载。展示层不能解释原话或把正文换成“更安全”的业务模板。 |

`bulk_no_confirmation` 当前以词语检测“跳过确认”，需退出自然语言权限路径。无论用户怎么说，提案本来就只能准备，最终提交必须经过可信确认。该硬约束由执行阶段保证，不能因有没有命中“无需确认”决定是否启用。

保留的规则包括 JSON Schema、联合键、字段白名单、金额精度、SQL 只读限制、鉴权、规则判定、幂等、状态机和审计。应移除的规则是以措辞决定业务动作、对象角色和会话接续的分支。任务和偏好工具继续沿用各自确认协议，不因为新意图声明跳过旧内容绑定。

## 七 正文和业务结果的统一出口

一次响应至少区分 `assistant_text`、`result_refs`、`system_events` 和实际执行状态。用户主要阅读模型正文；卡片呈现工具事实，回执呈现系统真实执行阶段。既有 CLI 文本汇总可以由展示层组装，但不能回写覆盖模型正文。

追问必须保留模型问句并保存对应缺项。信封类型与操作缺项冲突属于结构化协议错误，交回同一个模型修正，全轮最多一次；普通真实缺项直接追问，不消耗修正重试。模型提案成功后可以立即进入预览，无需额外模型调用润色预览。

Trace 同时保留实际模型输出、核验后的操作与来源、工具调用、协议失败、状态变化、最终展示字段和哈希。审计与回读只依据真实业务服务。保留所有旧脱敏要求，原始用户输入也不得绕过现有凭据脱敏。

## 八 迁移顺序和兼容策略

1. 建立能力清单：普通查询、汇总/筛选、规则解释、补号、更正、查改、任务、偏好、确认和审计回读。逐项标明现有入口、当前测试和所有者，避免只修三句却损失其他能力。
2. 先接通正文出口和共同意图协议，保持业务服务不变。先验证响应实际进入 TUI/CLI，再接入逐操作来源与范围。
3. 一次迁移查询、追问、补票和发票提案的自然语言入口，处理模型前工具开关、跨轮记录、提案校验与规则子集。迁移入口停用相应旧语义分支，失败不能自动回退。
4. 任务、偏好等管理协议通过同一能力清单检查兼容，沿用已有明确内容来源和可信确认。未迁移的自然语言适配器必须登记为遗留债务，不能声称它已经具备新泛化能力，也不能新增问法补丁扩大它。
5. 移除没有可信入口再使用的旧函数；确有可信 CLI 参数调用者时，保留明确参数适配，不保留“新方案失败就再猜一遍”的自然语言回退。

新结构可以在测试或显式指定候选版本中验证，不增加按关键词、问句或模型输出置信度选择新旧引擎的运行时开关。仅做必要的小范围提取，不顺带重写 SQL、任务、权限或 GUI。

## 九 小规模但有效的验收

测试矩阵覆盖业务结构和失效类别，语言样本用于抽样挑战。不会尝试穷举全部自然语言，也不会把每个变体写成独立路由。测试断言业务目标、范围、调用关系、待补状态和真实写入，不断言某句固定模板。

| 定向组 | 必须核验的性质 |
|---|---|
| 原三组失败回放 | 查询正文保留、修改缺项保存、独立修改目标进入正确预览。 |
| 等义与反义配对 | 随机换序改写结果不变；改为“只查”“不要改”后不可出现修改预览。 |
| 引用与字段值 | 转述不是本次执行要求；新值含“取消”“用途”等词不触发路由。 |
| 待补与更正 | 多轮补目标、改新值、切换企业、同句插入新查询，既不丢要求也不复用旧许可。 |
| 规则筛选与集合 | 完整集合、明确子集、排除、零匹配分别有真实证据，查得多不等于改得多。 |
| 边界与执行 | 含糊指代追问、错误引用拒绝、越权拒绝、取消零写入、一次确认提交及审计回读。 |
| 兼容与架构 | 已有任务/偏好确认和上下文引用未退化；业务服务不反向依赖运行时，无第二模型循环。 |

先离线重放原三组及定向因果用例，再用独立保留的三组业务题做 DeepSeek Live，每组发送前随机变换结构、语序和少量错字，保留种子、原始失败和实际输入。不向开发代码加入最终保留题的词句；模型不能充当金额、数量和权限的唯一评委。

## 十 防止继续堆积的完成条件

- 换一种自然语言表达，通常只新增或修改测试，生产代码无需增加问句、动作同义词或正则分支。
- 新增业务能力才改工具与业务服务；语言变体不新增业务工具或意图枚举。
- 原三组不再依赖句式适配器；查询、追问、补号和提案共用一个运行入口和一份待补状态。
- 没有隐式旧路由回退，完整保留普通查询、规则查询与合法预览流程。
- 模型正文可以沿 Trace 追到实际展示；提案沿真实选集、确认、审计和回读追到实际业务结果。
- 删除或隔离已替代的语义分支，并记录任务/偏好等尚存适配器的具体债务；不得把未迁移能力算作泛化通过。
- 首批离线、DeepSeek 和真人证据分别记录。三类证据通过前，NL-01 至 NL-06 不因文档完成而关闭。
