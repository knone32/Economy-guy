## 随机专项的实际调用链

### R01 查询正确但正文丢失

Trace `d4db62edeb294c0fafece10b2d4a5347`。

`get_invoice` 正确返回 C002 九月 F001、F009 的备注。模型随后返回合法的 `information` 信封，包含当前备注和只读说明。普通查询出口把正文换成 `render_information(read_results)`，`finish` 生成结果摘要，`TUI.finish_turn` 显示摘要。

这里的第一次丢失发生在 Agent 的输出选择，界面通过 `chat_notice` 延续了这次替换。改界面的显示字段无法恢复已经被上游丢掉的正文，需要同时修正 Agent 出口与界面消费方式。

### R02 追问状态与跨轮来源断开

首轮 Trace `4a2cf5e6617a4f4c9014c35481c4a0b0`，补充轮 Trace `c4fc39e74b2344f89a9a10a689c83f4f`。

模型查到了 F017、F018，并在正文中询问要改哪张，但把响应标为 `information`。运行时的 `scoped_edit` 未命中，`invoice_write=False`，最终按数据库查询处理，正文中的问题没有显示，`pending_intent` 也没有保存。

仅把记录中的响应类型修正为 `clarification`、补上 `missing_fields=[invoice_no]` 后，离线回放能显示追问，但 `pending_intent` 仍为空。原因是 `finish` 在 `invoice_write=False` 时，只保留企业、年份和月份等待补字段，票号被过滤掉。修正模型信封类型后仍有状态保存这一层阻断。

补充轮的模型通过历史消息理解了要求，重查 F018，并提出正确的备注新值。运行时却用当前短句重新构造修改范围。实际局部变量为 `requested.invoice_no=[F017,F018]`、`excluded=[]`、可信修改选集为 `{F018}`，模型声明保留的 F017 位于 `excluded_invoice_ids`。范围比较返回 `SCOPE_MISMATCH`。

模型能从历史读懂原要求，与运行时拥有一份可核验的待补记录，是两个不同的实现条件。当前缺少后者。

### R03 读取集合被当作修改集合

Trace `4956d4f8ec4647f98c9e194aff5d1e79`。

模型正确查询 F012、F015，并使用 F015 本轮查询返回的 `selection_id`，提出只改其备注的候选。重排后的表达未命中特定查改句式，`scoped_edit=None`。提案校验使用整句提取结果，把 `{F012,F015}` 当作应修改的集合，与候选 `{F015}` 比较后拒绝。

本次最先触发的错误是读写范围混合。错字本身没有使模型选错票号、字段或新值。

## 统一解决方法

采用同一个模型循环和一份经过运行时核验的业务语义记录，贯通回复、追问、接续与修改提案。

### 模型给出结构化业务含义

拟增加一个轻量的原生工具 `declare_business_intent`，让模型在执行查询前声明读取目标、独立写入目标、保留对象与字段、待补字段、接续动作，以及用户原话和前置查询的来源引用。它将候选意图交给同一个运行时校验器，生成本轮内部语义记录及引用编号。它只处理运行时意图数据，业务读取和修改继续调用现有工具。

声明与查询可在同一次模型响应的工具调用序列中按顺序执行。后续修改提案使用本轮语义引用与可信 `selection_id`，最终响应引用同一份记录。无需业务查询的直接追问可以在最终信封携带该意图，仍经过同一个校验器。这样可以在进入实际工具校验前保留语义角色，并控制额外模型往返。

模型为含糊目标留下待补字段。若语义记录表示仍需用户选择，最终信封必须使用 `clarification`。信封与结构化字段冲突时，把机器可检查的协议错误交回同一个模型修正，最多一次并计入现有预算。声明可与查询同批发出，实际往返次数在 Live 中核对。

### Harness 核验来源和执行边界

模型提供的语义记录属于候选数据。Harness 从当前可信账号、账簿、原始消息和已核验会话中检查引用，独立检查允许字段、新值原文字面量、读取范围、写入目标和实际查询结果，再生成内部 `ScopeProof`。

模型自报的身份、来源标签、权限、已确认或已提交状态不能生成许可。日期、票号和金额的格式归一及精确值校验继续使用结构化规则，业务动作与对象角色由模型表达。

`plan_invoice_change` 的自然语言入口使用核验后的独立写入目标。只读候选与修改集合的排除项分别处理，避免把整句票号合并成修改全集。`invoice_change_evidence` 在这条入口检查可追溯的字段与值来源，逐步替换依赖特定动词和完整句型的语义判断。每次提案继续检查当前权限、账期和本轮选集。

### 用已有会话状态保存可验证的接续信息

`pending_intent` 保存原始请求、已核验范围、候选对象、字段、新值来源、缺项和前置 Trace。模型的有效语义记录决定待补状态，状态保存不再依赖中文句式得到的 `invoice_write`。

补号、局部更正、新查询与自然语言取消统一由模型表达结构化接续动作。Harness 在现有查询链和待补状态上核验并执行，读取目标时重新查账。账号、账簿、会话边界、取消及新话题按真实状态处理，草稿与人工确认绑定当前执行阶段。Context Builder 继续负责组装上下文，Scheduler 继续负责预算。

### 设置单一模型正文出口

响应中设置独立的 `assistant_text`，保存通过协议校验的模型正文。Agent 的普通查询、追问和补票查询都写入这个出口。工作台显示该字段，结果卡、权限拒绝、确认窗口和操作回执使用已有结构化数据分别显示。`finish` 与 `chat_notice` 的兼容处理不得重写已经存在的模型正文。

事实引用、格式清理和脱敏在 Trace 中保留对应关系。模型文字不改变 Prepare、人工 Confirm、Commit、Audit 和新连接 Readback 的实际状态。模型通过原生工具提交修改提案后进入确认窗口，仍是合法执行流程。

记录原始 `model_reply`、核验后的语义记录、范围来源、工具调用结果和最终实际显示正文，以便判断模型是否真正参与决策与回复。

## 实施和验收范围

先定义共同语义记录与模型正文出口，再迁移普通查询、追问和补票查询，最后清理提前解释自然语言并直接返回业务答案的路径。复用现有查询工具、状态所有者、事务确认和审计机制，完成同一轮统一修复后提交一个代码版本验收。

原生提案仍需校验后才能进入预览。模型失败、没有最终响应、字段或票号错误时，保留明确失败状态及已有证据。可信确认按钮和确定性权限拒绝使用实际系统回执。

定向验收覆盖正文实际显示、有效追问与待补状态、补号与局部更正、自然语言取消、只查不改、读写范围分离、跨账号与会话隔离、错误模型提案，以及已有确认和审计回读。将固定模板字句断言替换为语义与调用关系断言，同时保留业务安全断言和现有架构检查。

首先重放本批固定种子及原实际输入。后续新专项先冻结业务预期，再在发送前随机调整结构、语序和少量错字，保留完整变形记录，每个变形只跑一次。Live 使用 DeepSeek `shared-flash`，首轮仍限三组、最多 12 次请求，协议修正计入预算。最终同版 Trace、隔离账簿和真人验收共同判定。

控制实验已验证现有后端可接受正确绑定的语义数据。模型按新协议生成该记录的稳定性、各入口兼容性及实际界面表现，需要统一修复完成后验证。
